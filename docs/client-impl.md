# 客户端实现现状

> `docs/client-spec.md` 是**最初的设计稿**，本文档记录**当前实际实现**。
> 两者冲突时以本文档为准。代码在 `src/js/game.js`、`src/js/level.js`。

---

## 一、相机

| 项 | 值 |
|---|---|
| 机位偏移 | `CAM_OFF = (-17, 21, -17)`（线头的西南上方） |
| 距离 / 俯角 | 约 31.9m / 41° |
| 朝向 | **世界坐标固定**，线头转向时相机不旋转（DL 的等距视角） |
| 跟随 | 平滑，`CAM_SMOOTH = 0.30` 秒（时间常数；2026-10-11 由 0.16 调大） |
| 中心 | **线头中点**（多线时取各线头坐标的平均；单线时就是线头本身） |
| 环绕 | 关卡写了 `cameraOrbit` 时，相机绕中点转方位角（不写则永远在正后方） |
| 拉远 | `cameraOrbit.zoom` 按时间轴把「相机到中点的距离」整体放大（两条线拉开时装不下） |

**平滑的关键做法**：相机位置与注视点使用**同一个**平滑系数，两者差值恒等于当前的 `off`——
偏移不变时（单线关卡）**视线方向永远不变**，只有跟随位置有滞后。线头在快速移动时略微偏离
画面中心，即“甩尾感”，画面本身不会旋转发晕。

```js
const k = 1 - Math.exp(-dt / CAM_SMOOTH);   // 指数平滑，与帧率无关
```

**逐项核对：哪些平滑了、哪些没有**（2026-10-11）

| 项 | 平滑 |
|---|---|
| 相机位置水平分量 `x` / `z` | ✅ 指数平滑，时间常数 `CAM_SMOOTH = 0.30s` |
| 相机位置垂直分量 `y` | ❌ **刚性**（`camPos.y = ty`），见下 |
| 环绕 / 拉远的时间曲线 | ❌ **分段线性、无缓动**：转折点（87 / 115 / 143 / 118 / 150 / 230 / 250s）速度突变 |
| 主题色过渡 | ✅ 逐帧 `lerp(0.035)`（⚠️ 与帧率相关，不是时间常数——144Hz 下会快 2.4 倍） |
| 瞬移白屏 | ✅ 按 `enter.fadeIn` / `fadeOut` 线性 |

- 折返点（115s）实测：相机角速度从 `+3.21°/s` 转到 `-3.21°/s` 约需 **0.9s**，
  峰值角加速度 **21°/s²** —— 这是 0.30s **跟随滞后**带来的柔化，**不等于**曲线本身有缓动。
  若要更柔和需显式给 yaw / zoom 曲线加缓动（代价：115s 附近不再是“相同角速度”）。
- 跟随滞后（用真实线头中点轨迹扫全曲，60fps）：
  | `CAM_SMOOTH` | 最大水平滞后 | 115s 折返峰值角加速度 | 归零用时(95%) |
  |---|---|---|---|
  | 0.16s（原） | 2.27m | 38.2°/s² | 0.5s |
  | **0.30s（现）** | **4.04m** | **20.8°/s²** | **0.9s** |
  滞后 ≈ `中点速度 × τ`：两条线同向时中点最快跑到 14 m/s，所以 τ=0.30 → 约 4.2m。
  这只是让线头在画面里往前偏一点点（4.2m ≈ 59m 可见宽的 7%），观感是更明显的“荡”。
- 复核过：τ 从 0.16 提到 0.30，**两条线是否全程在画面内没有变化**（模拟里最远线头到画面
  中心的距离 / 可见半宽，两个 τ 完全相同）。所以加大平滑不会把线推出画外。
- 有 `cameraOrbit` 时 `off` 本身在变，所以“视线方向不变”只在偏移恒定时成立；
  运镜要的就是这个朝向变化，平滑只作用在跟随位置这一层。

**三处必须直接吸附**（否则相机会飞）：首次进入、死亡重开、场景瞬移。

**垂直方向不做平滑**：线头坠落时掉得快，垂直若也平滑，相机会落后到看不见线头。
（副作用：拉远时相机高度以 0.66 m/s 匀速上升、零滞后，而 x/z 有滞后——量级只有 0.38m，看不出来。）

**环绕运镜（`cameraOrbit`）**：实现为**只改水平方位角**——相机到中点的水平半径（24.04m）
与高度（21m）全程不变，所以始终是一个圆弧，不会忽远忽近。参考系取
「两种行进方向之和」`dirA + dirB`（恒定的对角方向），于是玩家怎么转向相机都不会乱甩。
`start → peak` 匀速转到正右侧，`peak → end` 以同角速度转回；时刻表之外恒为正后方。

**拉远取景（`cameraOrbit.zoom`）**：两条线在后半段会拉开很远（`Breeze` 平均 34m、最大 73m，
而固定机位在 16:9 下只在注视平面上看得见约 59m 宽），所以按时间轴把**整条偏移向量**
乘以一个倍数（`start → peak` 拉到 `scale` 倍、`peak → hold` 保持、`hold → end` 恢复）。
乘在整条向量上意味着水平半径、高度、俯角全部等比放大——只是退后，构图与视线方向不变。
默认 31.92m 拉到 `scale = 2` 就是 63.85m，可见宽度约翻倍到 118m。

> ⚠️ `level.json` 里 `scenes[].camera`（`mode` / `height` / `dist` / `zoom_out`）
> **客户端目前不读取**——那是设计阶段留下的字段，实现时硬编码成了 `CAM_OFF`。

## 二、判定与死亡

判定分两步，**不是碰到边缘就死**：

```
线外沿越过路面外沿  →  开始下坠（重力 10）
                    ↓
        高架桥：摔到地面（y=0）即死
        贴地关：下方是虚空，掉够 FALL_DEPTH(10m) 才死
```

- 出界阈值：`(roadW + lineW) / 2` —— **只要线还有一点点搭在路面上就不掉**
  （曾用 `roadW/2`，那意味着线中心一到边缘就掉，而此时线还有一半在桥上）
- 下坠中忽略点击（掉下去救不回来）
- 死后 1 秒自动重开，从关卡开头

---

## 三、轨迹

**轨迹 = 玩家线头实际画出来的线，不是官方路线。**（这一点最初做错了，
按官方路线预生成，玩家一偏离就露馅）

- 线头每前进 **0.25m** 追加一个块，块的横截面 = 线头截面（贴着路面、高一个线头）
- 转向时：先补上“上一采样点→转角”的余量块，再放一个转角方块 → 无缝
- 全部塞进一个 `InstancedMesh`（上限 2 万块，本关全曲约 1 万），一次 draw call
- 下坠中不产生轨迹；瞬移不产生轨迹（采样点直接跳过去）
- 死亡重开轨迹清零重画

---

## 四、线头

- **正方体**，边长 = 线宽（1m）
- 与轨迹**共用同一个材质实例** `whiteMat`（受光照 `MeshStandardMaterial` + 轻微自发光），
  从根上杜绝色差
- 尺寸取 **1.02 倍**：线头始终与最新轨迹块重叠，尺寸完全相同时表面共面会 z-fighting 闪烁

---

## 五、引导线（独立元素类型）

- 画在路面上的**黑色虚线** + 每个转向点的**虚线方框**，合成一批 `LineSegments`
- 虚线节奏统一：画 0.125m 空 0.125m（方框为 1m 边长分 8 段、隔段画，正好也是 0.125m）
- WebGL 线宽恒为 1px，所以粗细天然一致
- 抬离路面 6cm；覆盖整条路线，关掉了视锥剔除
- 玩家恰好在顶点点击时，会从该方框位置扩散出一个黑色实线方框（扩大 + 淡出）

---

## 六、自动播放

- HUD 右下角「自动播放」勾选，设置持久化
- 在每个官方转向时刻自动 `doTurn()`，线沿官方路线走完全曲
- 开启时忽略手动点击，取消即恢复手动
- 精度：一帧误差造成约 **0.22m 的恒定相位偏移**，不累积，远小于出界阈值，不会掉下去

用途：预览关卡、检查路线、录屏发社区（不用自己练）。

---

## 七、高架桥

- 生成器 `--elevate H`：整条路架到 H 米高
- **桥面仍是等高的**（连续路面必须等高，只是整体抬升了一个常量）
- 桥墩沿路每 `--pier N` 米一根落到地面；地面是一层浅粉平面
- 好处：路在天上，地面可以自由布景；密集段路面交错看起来像立交匝道，
  而不是糊在地面上

---

## 八、渲染踩过的坑（重要，别再踩）

1. **动态 `count` 的 `InstancedMesh` 会被视锥剔除**
   `computeBoundingSphere()` 按**当前 count** 计算。轨迹创建时 count=0，
   包围球是原点上半径 0 的点；之后 count 涨了也不重算 → 相机走远后整条轨迹被剔除。
   → 动态 count 的网格必须 `frustumCulled = false`。

2. **相机 near/far 比值过大 → 深度精度不足**
   原本 `near=0.5 / far=3000`（1:6000），贴着路面的元素（只高出 1.5cm）被路面盖掉。
   → 改成 `near=2 / far=800`（雾在 460m 已全遮，够用），精度提升约 15 倍。

3. **两个物体表面共面 → z-fighting 闪烁**
   → `polygonOffset`（贴路面的元素）或尺寸差（线头 1.02 倍）。

4. **材质不同 → 色差**
   轨迹 `MeshBasicMaterial`（纯白）vs 线头 `MeshStandardMaterial`（受光照变灰白）。
   → 两者共用同一个材质实例。

## 十、多线关卡（双线玩法）

`level.lines[]` 给出多条线时，客户端把**渲染 / 输入 / 判定**三处都改成「遍历所有线」，
单线关卡会在 `linesOf()` 里合成一条线 A，走的是同一套代码，行为与从前一致。

**每条线自己一套**：`verts`（几何）、线头位置与朝向、坠落状态、轨迹 `InstancedMesh`、
线头立方体、引导线、方向 `dirA/dirB`（由该线 `spawn.dir` 推出）。

| 项 | 做法 |
|---|---|
| 路面 | 每条线各铺一条。**上下分层靠 `lines[].elevate`**（该线整体抬高 N 米，烘进 `verts` 的高度里）——两条路本来几乎平行、整段贴在一起，只有真抬起来才看清是两层。另加第 i 条整体下沉 `i × 0.004m` 作为**同高度时**的防共面兜底 |
| 颜色 | 线的材质由 `lines[].color` 决定（线头与轨迹**共用同一材质实例**，从根上杜绝色差）。白线给 `emissive 0x555555`，黑线保持纯黑 |
| 输入 | 每条线一个按键（`lines[].key`，`KeyboardEvent.code`）。默认 线 A `ArrowUp`、线 B `KeyX`；空格与鼠标左键仍等同线 A。玩家可在 HUD 里改，见「十一」 |
| 判定 | **逐线独立**：每条线跟自己那条官方路线比，任一条出界坠落到底整关失败 |
| 自动播放 | **可逐线单独开**，见「十一」。自动线按自己的官方路线解析（各线时刻表不同） |
| 瞬移 `teleports` | 只作用于线 A（顶层字段是单线时代的产物） |

**两条线是「各自独立时刻」**：各条线的转向点时刻/密度互不相干（`Breeze` 线 A 1034 点 / 线 B 705 点）。

> 密集踩音是高难关卡的常态，两条线各自 3.6 转/秒也**不是缺陷**，不要抽稀（见 `AGENT.md §14`）。

## 十一、操作按键与自动播放（HUD，逐线）

右下角两块控件，**都按「线的序号」一条线一份**（单线关卡就只有一份）：

```
                                    ┌──────────────────────────┐
                                    │ ■ 白线操作按键： ↑        │  ← 点一下进入录制
                                    │ ■ 黑线操作按键： X        │
                                    ├──────────────────────────┤
                                    │ 引导线  自动播放 白线  自动播放 黑线  音频延迟 │
                                    └──────────────────────────┘
```

**改键**：点按钮 → 按钮变成「按下按键…」（录制态，此时所有按键都被 `keydown` 拦下、
不再进游戏）→ 按任意键绑定，`Esc` / `Tab` 取消。
- **撞键自动互换**：新键若已被另一条线占用，那条线自动改回本条线原来的键（不会出现两线同一键）。
- 记忆存在 `localStorage` 的 `settings.keys`（数组，下标 = 线序号），
  关卡里的 `lines[].key` 只是**默认值**；`effectiveKey(i) = settings.keys[i] || game.lines[i].key`。
- 显示名按关卡给的颜色取（`#ffffff` → 白线、`#000000` → 黑线，其它 → 「线 A/B」）；
  `KeyboardEvent.code` 会转成好读的符号（`ArrowUp` → ↑、`KeyX` → X、`Space` → 空格）。

**逐线自动播放**：`Game.setAutoLines([true, false])` 直接控制每条线；`game.autoPlay`（旧的布尔字段）
保留为「所有线一起开关」的 getter/setter。推进逻辑里一条线**二选一**：

```js
for (const L of this.lines) {
  if (L.auto) { /* 位置 = vertAt(L.verts, t)，由音频时间解析，不累加 */ }
  else        { /* 位置 += 方向 × dt × 速度 */ }
}
```

- 自动播放的线**忽略手动输入**（`onTap` 里 `if (L.auto) return`），轨道也改走 `emitRouteTrail`。
- 开关存在 `settings.autoLines`；`settings.auto` 是旧存档的「全部一起」字段，读取时兜底，
  一旦玩家动过任何一条就整体固化下来（`setAutoLine` 先把当前生效值 materialize 再改）。
- 开始提示只列**需要玩家操作**的线；全开自动时提示「点击屏幕开始游戏（全部线都是自动播放）」
  （首帧仍要点击/按钮才开始，自动播放不会自己开始）。

## 十二、延迟校准（游戏内）

关卡里的 `latency_ms` 是**作者在自己设备上**校准出来的值（例如 Breeze 的 299ms）。
玩家换设备 / 换耳机（尤其蓝牙）就该自己测一遍，所以把采音器 `tools/BeatMarker.html` 的
校准器**同一套算法**搬进了关卡界面：右下角「音频延迟」按钮打开弹窗。

**三步**：点「开始校准」（每秒一声 1.2kHz 蜂鸣，间隔可切 0.5/0.75/1/1.5s）→ 跟着敲 `空格`
（至少 8 次，**怎么稳怎么敲，不用刻意等听到再反应**）→ 看「中位数 / 抖动」→「完成」保存。

| 指标 | 含义 |
|---|---|
| 中位数 | 建议的补偿值，正常范围 **100~500ms** |
| 抖动 ± | 稳定性。**<20ms 很稳，>50ms 说明敲乱了**，清空重测 |
| 条形图 | 每次敲击的偏差，红色 = 被剔除的离群值 |
| 本关作者校准值 | 从 `levelData.latency_ms` 读，摆在弹窗里给玩家做参考 |

**给玩家提供的「参考」**：弹窗里同时显示作者校准值，并说明「你实测的值会覆盖它；
清空输入框则回退到作者的值」（`settings.latency = null` = 用关卡自带值）。

**两个容易写错的地方**（都是从采音器踩坑后固化下来的）：

1. **匹配「最近响过的那一声」，不是「绝对值最近的」**：取最小的**非负**差值。
   用绝对值最近的话，延迟大时会错配到下一声，测值严重偏小、还看起来挺稳（见 `AGENT.md` §8 修复记录）。
2. **间隔固定 ≥0.5s**：半间隔 500ms 远大于任何合理延迟，从根上杜绝错配（ADR-5）。

**其他实现细节**：
- 校准独占 `空格`：`cal.active` 时 `keydown` 先拦下空格给校准，不再转线。
- **实时预览**：算出中位数就 `game.setLatency(med)`，边敲边能感受画面变化；只有「完成」才写 `settings`。
- 蜂鸣与音乐共用同一个 `AudioContext`，匹配用的是 `AC.currentTime`，所以音乐在放也不影响测量。
- 校准期间关卡仍在跑（会失败），建议在**首帧**（点击开始之前）做，弹窗里也写了这句提示。
- 打开弹窗时会先 `cal.samples = []`，避免上次的样本混进来。
- **顺带修的 bug**：`keydown` 现在会忽略 `INPUT/TEXTAREA/SELECT` 上的按键。此前在「延迟补偿」
  输入框里按 `↑↓` 调数字，会同时把线转掉、还被 `preventDefault` 掉步进。
- `返回` / `Esc` 退出关卡时会 `calStop()` 并关掉弹窗，蜂鸣不会跟到选关界面。
